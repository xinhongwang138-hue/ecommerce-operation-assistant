01 · 它是什么

一个运营工作台，外加八块「AI 到底能替人做哪一步」的答案

大部分 AI 项目停在「接了大模型」这一步。这个项目关心的是下一步：这一步该不该交给模型、错了会怎样、怎么让人一眼看出它错了。

业务上

店铺与商品、库存与竞品、AI 客服、会话考核、合同审批、直播切片、训练数据回流——运营一天里要碰的事，被拆成可独立进出的模块，共用一套身份与工作区。

不是八个 demo，是八个能在同一份数据上连起来的入口。

技术上

FastAPI + SQLAlchemy 的后端，Next.js 服务端组件的前端，MySQL 存业务、DuckDB 做分析仓、Redis 跑队列、LangGraph 管 Agent。

分析侧只读，写入只发生在仓内——慢查询不会拖住下单。

主张上

做不到的事不假装做到。平台不训练模型、不生成成片、不替人批合同，但它把「接进来要什么」写清楚，让边界可验证而不是靠嘴说。

这三条边界，各有一条 ADR 和一条实测证据。

02 · 八个模块

每个模块只回答一个问题，且答得能被追问

下面每张卡的「证据」行，都能在 _evidence/ 里找到对应的复算入口——不是「已完成」的自我评价，是跑过之后留下的数字。

01 / 数据中台

把「口径」变成一处定义

业务库只负责下单与录入，分析查询落在独立的 DuckDB 仓：ODS 原样落地 → DWD 清洗去重 → DWS 主题汇总 → ADS 直接出指标。

同一个 GMV，在页面、导出、问数三处必须是同一个数。所以口径只有一处定义，公式与取数表写在同一个文件里。

证据 E03 · 对真实 MySQL 跑批，不是 SQLite 夹具
02 / 问数

模型只写一条 SELECT，且不享受内部通道

中文提问 → 模型生成 SQL → 过与手敲 SQL 完全相同的护栏（单条 SELECT / 表白名单 / 最多 500 行）→ 只读连接执行。

模型是「会写 SQL 的陌生人」。护栏只有一份，换模型不需要重做安全评估。

证据 E10 · 加一行字段释义，口径从错变对
03 / 知识库

每条命中都能指回原文的字符区间

落在本仓的一套 RAG：按句切片并记 char_start/char_end，BM25 与向量混合检索，引用片段逐字校验。

模型给的引文在原文里 in 不成立就丢弃并计数——宁可少答，不编答案。

证据 E13 · 向量端点抖动：21,451ms → 686–884ms
04 / AI 客服

三条出口，加一条「宁可不答」的底线

转人工 / FAQ / 检索三轨道分流；命中不足不是硬答，而是拒答并给出最接近的相似度，再引导转人工。

拒答线 0.36 不是拍的：实测相关最低 0.3882、无关最高 0.3378，空隙只有 0.05，取中点。

证据 E16 / E17 · 四条出口逐条走一遍
05 / 销售考核

五条规则打分，红线一票否决

导入客服会话即评分：意图命中、行动号召、语气、长度、红线。坐席排行榜与单会话报告，分数只由 rescore 改。

历史报告不会因为改了规则就变分——rule_version 标出来是哪版规则打的。

证据 E15 / E18 · 一次字面重合导致的误判与返工
06 / 合同审批

规则分与语义分分开记，审批是留痕

上传即切条款，规则命中与模型读出的单向约定分成两段记录；高风险条款要「通过」必须写理由，两条记录各存一份 13 条风险快照。

两个分数的分母不同，加起来没有意义——只合并展示层级，不合并数值。

证据 E19 · 同一份合同两次审批的留痕
07 / 直播切片

只挑不剪：给出时间码，不给成片

吃进带时间码的转写，按卖点密度、开场钩子、行动号召、时长合规四维加权，每条候选附起止秒数与命中理由。

判断「哪段值得发」比「把这段切干净」稀缺得多，裁剪交给下游工具。

证据 E20 · 48 句转写 → 8 条候选，含一次边界返工
08 / 模型微调

平台不训练，但把接训练的两个缝留对

样本从质检与客服回流，去重、按「该不该学」分层、导出 OpenAI chat 格式 JSONL，训练前后用同一批题对照评测。

needs_fix 不进导出——拿去训等于教模型学错误的回答。

证据 E21 / E22 · 13 条样本 11 条被合并；执行器真跑一轮

03 · 深挖四个

值得展开的不是「做了什么」，是「当时还能怎么做」

下面四个案例都发生过返工。保留返工过程，是因为它比结果更能说明判断是怎么形成的。

CASE A · 直播切片

边界不能只靠时间窗

规则 1.0.0 → 1.0.1

问题

规则从锚点向右扩到「够长」就停，停下来时不判断那句是在讲卖点还是在收场。真实场次里，一条候选的结尾变成了「小黄车还有最后 50 件。抢完就下架。我们下次见。」——剪辑师拿到手还得自己回退 5 秒。

取舍

没有引入语义模型，而是用一张道别词表加三条自我约束：不动含卖点词的句子（边界那句本身可能就是锚点）、削短了往左补（切片必须连续，不能跳句）、补不出来就整个退回（宁可多带一句道别，也不交 8 秒碎片）。只削尾巴不削开头——往右扩会冲过头，往左补是「补到够长就停」，天然不越界。

3:303:454:00
修复前
3:44 – 3:59

修复后
3:39 – 3:54

把结尾那句「我们下次见。」削掉，只剩 10 秒（低于 12 秒下限），于是往左补一句「过点恢复 199」，总长回到 15 秒（两条都是 15 秒）——整体前移 5 秒，长度不变。

该场 rule_version=1.0.1，6 条候选一条都不带道别

CASE B · 模型微调

「不训练」不等于「没做完」

回调 + 执行器两个缝

问题

没有 GPU，第一版只能回答「本平台不执行训练」，回答不了「那到底怎么接」。面试官和同事都会追问这一句，答不上来就等于没做完。

取舍

不假装训练，留两个缝：回调让训练机把结果写回台账，执行器把「导出数据 → 调训练器 → 回写状态」串起来。读走库、写走回调——如果执行器也直接改库，回调协议就永远没有真实流量压过，接第三方训练机时才会发现签名算错了。

登记作业数据集 #3 · qwen-plus
导出 JSONL去重分层，待修样本排除
跑训练器命令由环境变量决定
HMAC 回调签名覆盖 job_id + 原样请求体
写入台账状态、指标、日志尾巴

取舍落在状态码上

场景行为为什么
同一状态回写两次200 · 不改字段训练框架会重试，第二次的空 metrics 不能把第一次的清成 {}
已完成又被写成 running409两边认知不一致要让台账说出来，不能悄悄改口
启动即失败允许 registered → failed这也是真实结局，不逼着先改成 running 去凑中间态
没配回调密钥503它能改台账，等于凭据，不能因为「忘了配」变成谁都能写

证据

失败

CASE C · 问数

一行释义，把「不报错的错」挡住

_COLUMN_NOTES · 7 条

问题

模型写 SQL 最难防的不是语法错，是「列名对、口径错，而且不报错」。问「失败率」，它写出 success_rate AS 失败率——表里有这列，SQL 能跑，数字全反。

取舍

没有做全量数据字典（维护不动，也没人看），只登记名字会骗人的列：反向语义、0 值有特殊含义、行级与汇总级含义不同。同一个问题、同一个模型，只加一行释义的结果：

生成的 SQL结果
加释义前success_rate AS 失败率口径错，不报错
加释义后success_rate AS 成功率, (1 - success_rate) AS 失败率正确

证据

同一句问题、同一个模型的前后对照记在 E10。这也是「模型判断能被真正约束住」的少数几处之一——不是靠 prompt 劝它小心，是靠把口径写进它读得到的地方。

CASE D · 考核与客服

中文没有词边界，红线会咬到自己人

误判 → 词表 → 阈值

问题

红线靠关键词，而 "滚" in text 会命中「主图回滚」。P01 的会话流进 P09 之后才暴露：AI 助手被判了 3 次辱骂、最差 0.0 分——同一条数据被两个模块消费，才看得出规则的问题。

取舍

单字关键词要么换成完整短语，要么登记进 REDLINE_BENIGN_COMPOUNDS。红线是一票否决，误判的代价不对称：漏判是内容风险，误判是让人白背一次处分。

拒答线也不是拍的

两篇真实资料入库后，问 4 组相关问题、4 组无关问题，看 top1 分数：相关最低 0.3882，无关最高 0.3378，空隙只有 0.05，阈值取中点 0.36。两条判据刻意不对称——词法命中只看有没有匹配到词（BM25 分数量纲随语料变），纯向量命中才比 0.36（余弦有稳定量纲）。

证据

误判的三条会话与修复记录在 E18；阈值那张分布表与阈值写在同一个文件里，因为必须一起维护（E17）。

04 · 工程约定

28 条约定，都是被坑出来的

仓库里有一节「改代码前先看」，编号到 28。挑六条，因为它们分别代表一类错误：时钟、口径、信任、边界、平台、凭据。

01

时间戳必须同源

created_at 走数据库时钟，补「事件发生时间」时也用它。掺一个 Python 的 datetime.now(UTC)，两个字段一减就差 8 小时——cs_tickets 上实测 -28800 秒。

02

两段分不要加成一个分

规则分与语义分的分母不同（一个是我们登记过的规则，一个是模型读出的单向约定）。要合并只合并展示层级，不合并数值。

03

模型给的引文必须逐字校验

合同复核的 quote、RAG 的引用片段走同一条规矩：在原文里 in 不成立就丢弃并计数。不要让模型「概括条款」。

04

算法修不好的地方要留给人和流程

切片边界 1.0.1 只治「结尾恰好是道别」这一种，开头拖沓、中段跑题仍然治不了——所以「人工定稿」是必需步骤，不是可选项。

05

跨平台先怀疑切分，再怀疑业务

Windows 上 shlex.split 的默认 POSIX 模式把反斜杠当转义，D:\learning\... 被啃成 D:learning...，训练器一启动就报「数据集不存在」。

06

能改台账的接口就是凭据

回调没配密钥一律 503，绝不「默认放行」；签名里必须带 job_id，否则同一份 {"status":"succeeded"} 能贴到任何作业上。

05 · 证据是怎么留的

不存截图，存能重跑的命令和当时的输出

截图会过期，也会骗人——它证明不了那张图是不是手改的。_evidence/INDEX.md 里 22 条记录，每一条都是「命令 + 原始输出 + 如果不对该怎么看」。

类别例子为什么这样留
真实链路 对真实 MySQL 跑批、真实 text-embedding-v4 入库与检索 夹具能过、真机过不了，是最常见的假绿
失败也要留 job #3 退出码 2；向量端点抖动 21,451ms 只留成功记录，等于把「退出码是编的」这件事留给别人猜
页面级 生产构建抓 HTML，检查首屏关键词、失败标记、可见文本里的 undefined SSR 失败会降级成客户端渲染，页面看着能开、内容却是空的
回归 切片去重的对照组；考核改判据前后的同一批会话 没有对照，就分不清「改好了」和「改巧了」

写文档时也按这条规矩来：凡是「实测」两个字后面的数字，都能在证据索引里对上；对不上的，当时就改文档——本轮就改过一次，把「7 条候选」改成实际的 6 条（另 1 条属于另一场）。
