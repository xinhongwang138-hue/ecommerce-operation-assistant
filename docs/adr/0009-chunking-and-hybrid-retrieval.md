# 0009. 切片与检索：向量存 JSON、两路名次做 RRF

- 状态：Accepted
- 日期：2026-10-30
- 影响范围：`api/app/rag/chunking.py`、`api/app/rag/tokenize.py`、`api/app/rag/retrieval.py`、`api/app/rag/embedding.py`

## 背景

要让 `/rag` 真的能回答"上个月那版素材为什么不行"，必须解决四件事：切多细、怎么切、怎么排、排不出来怎么办。每一件都有"看起来更专业"的选项，而那些选项在这个仓库里都会引入新的失败模式。

## 决策

### 一、按句切，target 是软上限

切分单位是句子（`。！？；\n`），`target=320` 是**软上限**而不是切点：攒句子攒到超过 target 才落一片，`max_chars=480` 兜底。相邻片之间回退到 overlap（48 字）以内，保证跨片的一句话不会两边都读不到。

关键细节：**剩余内容一屏装得下就整段收尾**。曾经一篇 329 字的复盘被切成 `[0,284]` 和 `[181,329]`，重复 103 字；两片在检索里互相抢名次，问"素材哪一版更好"时把库存那段排到了第一。软上限的意义就是允许最后一片超一点，换取"同一件事只出现一次"。

每片都带 `char_start` / `char_end`。没有字符区间的检索结果只能叫"相关段落"，不能叫引用。

### 二、中文用 bigram，不用 jieba

`tokenize()` 对 CJK 取相邻二字，对 ASCII 取整词（小写下划线与数字保留）。不用分词器的原因是**行为可控性**：jieba 的词典不在版本控制里，同一条 query 在不同机器上可能切出不同的词，检索结果就变成了"在我机器上对"。bigram 的召回率更高、噪声也更多，但噪声由 BM25 的 IDF 和 RRF 的名次融合吸收。

### 三、向量存 JSON 数组，不引入向量库

`rag_chunks.embedding` 是 `LONGTEXT` 里的 JSON 数组，检索时全量载入算余弦。上限 `MAX_SCAN_CHUNKS = 5000`；超过这个量级就换向量库，不在这里硬撑。

理由是这个仓库的数据规模：一个 workspace 的运营资料是几十篇到几百篇，切片数在千级。为千级数据引入一个独立服务（Milvus / Qdrant / pgvector 扩一套 Postgres），换来的是一个新的部署依赖、一个新的备份对象、一个新的故障点。而省下的那点查询时间，用户感知不到。

### 四、两路召回用 RRF 融合，只用名次不用分数

BM25 的分数是无界的，余弦相似度在 `[-1, 1]`。想把它们加权求和，就得先归一化，而归一化的参数会随语料漂移——今天调的权重，明天语料一换就错了。

RRF（`score = Σ 1/(k + rank)`，`k=60`）只看名次，天然免疫量纲差异。它不需要调参，也不需要在语料变化后重新校准。

### 五、向量是增强项，失败必须降级且必须说清

- `embed_texts()` 不抛异常，错误挂在 `EmbedOutcome.error` 里；入库照常成功，只是 `embedded_chunks = 0`。
- 检索时向量不可用就走纯词法，`SearchRead.warnings` 如实写明原因，前端展示。
- **超时必须短到用户还愿意等**：读 8 秒、连接 3 秒。实测一次网络抖动在连接阶段会让检索卡 **21 秒**——用户等不到结果，等于功能不可用。
- **失败后熔断 30 秒**：抖动通常成串出现，逐次重试只会让这段时间里每一个请求都变慢。冷却期内直接返回"跳过"，不再建连接；成功一次即恢复。

## 后果

- 得到：没有 `EMBEDDING_MODEL` 也能跑（纯 BM25），配了就连向量，端点抽风时最坏多花 3 秒然后降级。三种状态都不需要改配置或重启。
- 得到：每条命中都能指回原文的字符区间，可以拿 `content[char_start:char_end]` 逐字核对。
- 付出：切片上限意味着十万级资料要换实现。这是**已知的天花板**，写在常量注释里，而不是等它悄悄变慢。
- 付出：bigram 的召回噪声会让短 query（两个字的词）命中一些无关片。靠 `top_k` 与名次融合过滤，不追求单条 query 的完美。
