# 0012. 考核只读快照：导入幂等、重算显式

- 状态：Accepted
- 日期：2026-10-30
- 影响范围：`api/app/qa/service.py`、`api/app/api/routes/qa.py`

## 背景

考核数据有一个特性：**它会被拿来对人**。所以"分数怎么变的"这件事本身要被约束，否则会出三类事故：

1. 同一批会话被导入两次，排行榜里同一个人有 2 倍会话量，平均分被稀释。
2. 上游补录了一条消息，历史月份的分数跟着变，已经发出去的奖金对不上账。
3. 规则改了之后，所有人打开旧报告都看到新分数，没人说得清"上个月为什么是 72"。

## 决策

**导入幂等，键是 `(workspace_id, external_id)`。** 重复导入只更新不新增；会话内容以最后一次导入为准（先清空旧消息再写入），避免上一版多出来的句子残留成证据。被跳过的会话写进 `warnings`，不静默吞掉。

**时间戳缺失的会话整条跳过，不补当前时间。** 补一个"现在"会让三年前的会话混进本月榜单——这比不导入更糟。

**评分只发生在两处**：导入之后、显式调用 `POST /qa/rescore`。所有读接口（summary / sessions / report / leaderboard / export）都不顺手改数据。打开一次报告就刷新一次分数，是最难查的一类"分数自己变了"。

**规则版本随分数落库。** `qa_scores.rule_version` 记下这条分数是哪一版规则算的。改规则后必须重算，历史报告的分数不会自己变。

**考核只读会话快照，不回读业务表算分。** 分数来自 `qa_sessions` / `qa_messages` 里的原文，不依赖 `performance_records` 或分析仓——会话是考核的事实来源，业务数据是经营的事实来源，两者混用会让"为什么这个月分数变了"永远说不清。

**来源可区分。** `source_kind` 只有两个值：`import`（外部客服系统导出）与 `agent`（本仓 `agent_conversations`）。本仓没有人工坐席，所以从 `agent_conversations` 拉来的会话统一挂在"AI 助手"名下——这不是虚构考核对象，而是事实：那些回复确实由 AI 发出。没有会话时 `imported=0` 并给出原因，**不造样本**。

## 后果

- 得到：重复导入安全。运营多发几次导入请求不会污染榜单。
- 得到：`POST /qa/rescore` 是唯一能改历史分数的入口，且走 edit 权限，有痕迹。
- 付出：规则改动后旧报告仍是旧分数，用户可能看到"报告分数与规则版本不一致"。这是刻意的——不一致是可以解释的，静默刷新则不能。
- 付出：会话内容以最后一次导入为准，"修正一条错别字"也会覆盖整条会话。对质检场景可接受：质检对象是这次会话的完整文本，不是增量。
