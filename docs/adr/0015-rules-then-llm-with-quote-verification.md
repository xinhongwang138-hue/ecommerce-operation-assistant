# 0015. 规则打分 + 模型复核：两段分开，引用必须能在原文里逐字找到

- 状态：Accepted
- 日期：2026-10-30
- 影响范围：`api/app/contracts/rules.py`、`semantic.py`、`scoring.py`、`service.py`

## 背景

合同审阅要做两件不同的事：

1. 数出可量化的东西——账期 90 天、定金 50%、违约金 40%、没有验收条款；
2. 读出需要理解的东​西——「以甲方确认为准」把判断权交给了一方，「及时交付合格产品」每个词都还要再解释一遍。

第一件事规则能做，而且做得比模型好：可复现、可争论、改一条规则就能验证影响面。第二件事规则做不到，它对措辞没有理解。

所以直觉是"规则 + 模型一起上，分数加总"。但直接加会出两个问题。

**问题一：模型会编原文。** 让它"引用触发这条判断的句子"，它会给出一句意思相近、原文里并不存在的话。审批人拿着这句话去合同里找，找不到，然后整份报告就作废了——不是那一条作废，是全部。

**问题二：模型总能找出东西。** 实测一份刻意写好的、规则零命中的合同，语义复核仍然报了 4 条、2 条高危，总分 92。回头看这 4 条大多成立（违约金只约束乙方、付款与交付脱钩），但它们和"账期 90 天"不是同一类证据：后者任何人打开合同都能核对，前者需要人来判断成不成立。

把两者加成一个数，等于宣称它们一样硬。

## 决策

**一次抽取，两段复核，分数分开记。**

```
上传 ──► 切条款 ──► 规则（同步，立即出结果）──► 规则分
                        │
                        └─► 语义复核（显式触发，慢，会失败）──► 语义分
                                                                    │
                                                    总分 = min(100, 规则分 + 语义分)
```

三条硬约束：

**1. 每条风险的 `source` 必须落库，是 `rule` 还是 `llm`。** 报告里两者分色显示。混在一起，整份报告的可信度会掉到模型水平。

**2. 模型给的 `quote` 必须在合同正文里逐字出现，否则整条丢掉。** 校验前只抹平空白与全/半角引号（模型常把换行变成空格），除此之外一个字都不放过。丢弃条数与原因要回给调用方——"模型没看出问题"和"模型瞎说被过滤了"在报告里必须长得不一样。

**3. 不把语义复核做成上传流程的一环。** 上传要快、要能重试；模型调用 17 秒且会失败。分开之后，语义复核挂了也不影响已经拿到的规则结论。

超长合同只送前 12000 字，并在 prompt 里明确告诉模型"后面你没看到，不要下结论"。悄悄截断会让它对没读到的部分编造判断。

## 后果

- 得到：规则分可以逐条摊开争论。十条规则各自独立、纯函数，改一条重跑一遍就知道影响面。
- 得到：模型编的引用不会进报告。实测一份 13 条风险的合同，模型给了 5 条、丢弃 0 条——因为那 5 条引用的都是原句；而构造的假引用在测试里被稳定丢掉。
- 得到：分数能拆开看。同一份合同「规则 0 + 语义 92」比「92 分」信息量大得多：前者说明结构上没问题，值得谈的是那 4 条语义条款。
- 付出：两段分数之和仍然封顶 100，所以"5 条高危"和"13 条风险"都显示 100。这是有意的：到了这个程度，区分谁更差没有决策价值。
- 付出：语义复核的结果不可复现。同一个 temperature=0.2 跑两次，条目和措辞都会变。所以它不能进考核、不能进合同台账的硬指标，只能作为"该看这几条"的线索。
- 重新考虑的条件：如果接入带引用能力的模型（能返回 span 偏移而不是文本），可以把 `quote` 校验从字符串包含升级到区间重叠，误杀率会降低。
