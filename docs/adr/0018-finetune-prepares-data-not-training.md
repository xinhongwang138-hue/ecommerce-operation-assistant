# 0018. 微调平台只准备数据，不执行训练

- 状态：Accepted
- 日期：2026-10-30
- 影响范围：`api/app/finetune/builders.py`、`api/app/finetune/service.py`、`web/src/components/finetune-panel.tsx`

## 背景

"模型微调平台"这个名字自带承诺：点一下，模型变好。真要兑现，需要 GPU、训练框架、checkpoint 管理、显存调度、断点续训——这是一整个 MLOps 系统的量级。

而且一个更根本的问题：**训练本身不是瓶颈，样本才是。**

在真实业务里，卡住的从来不是"跑不了训练"。租一台 A100、拉一个 LLaMA-Factory，一下午就能跑起来。卡住的是：

1. 拿不出一条像样的训练数据。会话散在 P09 质检表、P01 客服表、导出过的 Excel 里，字段不一样、时间对不上。
2. 拿出来的数据是脏的。同一句模板话术重复三遍，模型就只学会那一句；一条"不知道，自己看详情页"的差评响应混进正向样本，等于教模型学骂人。
3. 训完了不知道有没有变好。换一批题测，"变好了"可以归因到任何东西——换了题、换了温度、换了心情。

这三件事没有一件需要 GPU。它们需要的是：**可追溯的样本、入库前的去重与分层、同一批题的对照评测。**

## 决策

**平台负责四件事，不碰第五件。**

```
✅ 回流：从 P09 质检会话、P01 客服会话按需取样
✅ 加工：去重（指纹级）、长度过滤、质量分层（正向 / 边界 / 待修）
✅ 导出：OpenAI chat 格式 JSONL，待修样本排除在外
✅ 台账：任务登记、状态推进、同批题对照评测（base vs tuned）
❌ 训练：不执行，不出现在本平台
```

**每条样本必须可追溯。** `source` + `source_ref` 指回原始记录（`qa_session:16`、`cs_conversation:3`），`fingerprint` 是消息内容的 SHA-256。训练数据说不清来源，就没法回答"模型为什么会这么说"，也没法在下游投诉时把那条样本撤掉重训。

**质量分层按"该不该学"分，不按分数高低分。**

| 层 | 来源判据 | 用途 |
| --- | --- | --- |
| positive | 质检 A/B 级；客服轨道为 faq / retrieval | 进训练集 |
| boundary | 客服轨道为 refuse / handoff——教"什么时候该停" | 进训练集 |
| needs_fix | 质检 C/D 级或有红线 | **不进导出**，留档待修 |

把待修样本拿去训，等于教模型学错误的回答。这类样本在真实数据里最少（拒答、转人工），也最值钱——它们教的是边界。

**评测必须同批题。** `record_eval` 一次收一批 `{question, base_score, tuned_score}`，算平均分差、胜/负/平。换一批题再测，两次的 delta 不可比。

## 后果

- 得到：从"想微调"到"有可用的 JSONL"是一条几十秒的链路，不需要 GPU、不需要运维。
- 得到：数据集快照里写着这次为什么只有 13 条——`skipped` 记丢弃原因，`duplicates_by_source` 记去重丢的是哪一侧。**静默丢弃是数据平台最坏的失败方式**：只看到"这次只有 13 条"，没人知道另 11 条去哪了（实测本机 11 条客服会话与质检会话逐字相同，全部被合并）。
- 付出：链路没有闭合到"模型上线"。训练由外部服务执行，状态和指标靠人/回调填回来。平台不画进度条、不画 loss 曲线——画一条假的比不画更糟，它会让人以为在等一个结果。
- 付出：`metrics` 是自由 JSON，没有校验。不同训练框架的指标名不一样，强行统一只会逼人填假数据。
- 重新考虑的条件：如果样本量稳定在万级以上、且训练频率高于每周一次，值得把训练编排接进来（排队、重试、checkpoint）。但那是另一套系统，不该长在这个平台上。

## 相关

- 去重时保留 P09 侧而非 P01 侧：质检会话带分数、等级和红线标记，标签比轨道更硬。
- 长度只数对话本身，不算 system prompt。把固定模板算进去会让 `MIN_CHARS` 永远命中不了——"在吗/在"这种两个字的会话也能通过过滤（实测踩过）。
