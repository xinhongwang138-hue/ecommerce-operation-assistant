# 0010. 自建 RAG 与外部智库并存，不互相替代

- 状态：Accepted
- 日期：2026-10-30
- 影响范围：`api/app/api/routes/knowledge.py`（外部）、`api/app/api/routes/rag.py`（本仓）

## 背景

`/knowledge`（掌柜智库）是把文档交给**外部服务**做解析、切片、索引，本库只存映射关系与状态；检索走 `knowledge_proxy`，答案和引用都由上游给。

P04 的诉求是"这套东西得在我自己的仓里能跑起来、能讲清楚每一行"。于是出现一个问题：既然 `/knowledge` 已经能用，为什么还要在仓内再写一套 `/rag`？

## 决策

两者并存，定位不同，谁都不吞掉谁：

| | `/knowledge` 外部智库 | `/rag` 本仓自建 |
| --- | --- | --- |
| 索引在哪 | 上游服务 | 本库 `rag_documents` / `rag_chunks` |
| 能力范围 | PDF / 图片 / 复杂版面解析、跨项目语料 | 纯文本与 Markdown |
| 依赖 | 需要智库服务与内部服务令牌 | 只要数据库；向量端点可选 |
| 可解释性 | 拿到的是上游返回的结果 | 切片、名次、字符区间全部可查 |
| 故障面 | 上游不可用时整条链路不可用 | 降级为纯词法，功能不残缺 |

判断标准不是"哪套更强"，而是**这段资料属于谁**：

- 跨项目、跨团队、需要复杂版面解析的长期资料 → `/knowledge`，交给专业服务。
- 这个 workspace 自己的运营复盘、竞品周报、活动方案 → `/rag`，落在自己的库里，跟着租户一起备份、一起删。

## 后果

- 得到：`/rag` 不依赖任何外部服务就能跑通"入库 → 切片 → 检索 → 引用回溯"，这条链路在离线环境里也能演示和测试（有 23 项测试守着）。
- 得到：`/knowledge` 的价值没有被稀释——PDF 解析、版面理解这类事本仓不做，也不该做。
- 付出：两套入口，用户需要知道区别。缓解办法写在页面上：`/rag` 明确标"本仓自建"，`/knowledge` 标外部智库。
- 付出：两套切片/检索实现不会自动同步。这是接受的——它们本来就是两个不同的系统，同步反而是错觉。真正需要一致的是**租户隔离**：两者都用 `workspace_scope`，缺 workspace 一律 403，跨租户命中一律 404。
