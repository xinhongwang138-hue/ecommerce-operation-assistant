# 0007. 模型写的 SQL 当不可信输入

- 状态：Accepted
- 日期：2026-10-30
- 影响范围：`api/app/nl2sql/`、`app/api/routes/nl2sql.py`

## 背景

NL2SQL 的常见实现是「模型生成 SQL → 直接执行 → 返回结果」。模型是我们自己调的、prompt 是我们自己写的，于是很容易给它开一条"内部通道"：跳过护栏、放宽行数、允许临时表。

这条通道一旦开了，风险的形状就变了。模型的输入是用户的问题，用户可以说"把这张表清空看看会怎样"；模型也可能自己写出 `CREATE OR REPLACE`（它知道建表语法），或者为了"方便"读一个 CSV。这类错误不来自攻击，来自模型把「你觉得怎样都行」当成许可。

## 决策

模型生成的 SQL 与用户在查询框里手敲的 SQL 走**完全相同的一条路径**：`warehouse.guard_select` → `execute_guarded`（只读连接 + 强制 `LIMIT`）。没有特权分支，没有"内部可信"标记。

```
问题 → 模型 → SQL ─┬─→ guard_select ──→ execute_guarded(read_only) ──→ 结果
手敲 SQL ──────────┘
```

护栏只有一份实现。两份就会不同步，而不同步的那一刻就是漏洞。

## 后果

- 得到：模型的能力边界被钉死在"只能读、只能读自己租户、只能读 500 行"；换模型（qwen / deepseek / 任何兼容端点）不需要重新做安全评估。
- 付出：护栏的误杀会同时打到问数和手写查询。这是可接受的——报错里写清命中了哪条规则，改个写法就能过。
- 配套：失败只重试一次（`MAX_ATTEMPTS = 2`）。第一次失败的原因是"不认识表"，第二次通常还是不认识；再往后该改的是 prompt 或目录，不是继续重试。
- 配套：两次都不通过时返回 **422** 并带上每一轮被拒的原因，而不是 500。用户看到的是"因为什么不行"，不是"生成失败"。
