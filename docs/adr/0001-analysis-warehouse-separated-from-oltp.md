# 0001. 分析仓与业务库物理分离

- 状态：Accepted
- 日期：2026-10-30
- 影响范围：`api/app/dataplatform/`、`api/warehouse/`

## 背景

业务数据在 MySQL，运营看板要按日、按店、按商品多维聚合。两条路：

1. 直接在 MySQL 上写聚合 SQL，让看板查业务库；
2. 把数据抽到独立分析仓，看板只查仓。

路线 1 的问题不是「慢」，而是**慢查询和业务事务抢同一批连接与锁**。一次误写的全表扫描能让下单接口超时；补录一周数据时，聚合 SQL 又必须绕开正在写入的行。此外分析侧需要窗口函数、`QUALIFY`、`PIVOT` 之类的表达力，MySQL 8 上要么写不出来，要么写得没法维护。

## 决策

业务库与分析仓物理分离。分析仓用 **DuckDB 单文件**（`api/warehouse/workspace_<id>.duckdb`），列存 + 向量化执行，跑批与查询都在仓内完成。`dataplatform` 对 MySQL 只读，写只发生在仓里。

## 后果

- 得到：分析查询打不到业务事务；仓内可以用窗口函数和列存优势；单文件便于备份、拷贝、按租户隔离。
- 付出：数据有一份冗余副本，存在「仓落后于源库」的时间窗。因此**必须**跑批，且跑批是显式动作而不是查询时隐式发生——用户看的是「上次跑批的快照」，不是「此刻的真实」。这一点写进了 `/data-platform` 页头（上次跑批时间 + 耗时 + 抽取行数）。
- 重新考虑的触发条件：需要秒级实时看板，或单租户数据量超过单机内存。届时换 ClickHouse / Doris，`pipeline.py` 的建表声明可以平移。
