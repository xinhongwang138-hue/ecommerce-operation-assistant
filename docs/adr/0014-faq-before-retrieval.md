# 0014. FAQ 排在检索之前：确定性知识不能被排序影响

- 状态：Accepted
- 日期：2026-10-30
- 影响范围：`api/app/cs/faq.py`、`api/app/cs/service.py`（`_route`）

## 背景

「多久发货」「包邮吗」「怎么退货」这类问题占了客服进线的绝大多数。它们的答案有个共同点：**运营已经定死了**。48 小时发货、满 49 包邮、7 天无理由——这些不是"从资料里检索出来的相关内容"，是承诺。

最自然的做法是把这些答案也写成文档，扔进 RAG 语料，统一走检索。这样只有一条路径，代码也更少。

实际这样做会踩三个坑。

**一是排序会改答案。** 语料里同时有"发货说明"和"大促活动规则"，后者提到"预售商品 72 小时内发出"。向量检索把活动规则排在前面，客户问"多久发货"就被告知 72 小时——错，现货是 48 小时。答案对不对取决于检索排名，这在承诺类问题上不可接受。

**二是向量端点抖一下就答不出来。** 检索依赖 embedding 端点，ADR 0009 之后的实现给它加了 8 秒超时和 30 秒熔断。熔断期间所有检索请求直接降级为"仅词法"。如果 FAQ 也在检索里，那 30 秒里连"包邮吗"都答不出——而这条答案根本不需要任何外部依赖。

**三是改写过的答案没法追溯。** 客户投诉"你们客服说 7 天无理由"，运营要能定位到原话。FAQ 里存的是定稿文本，检索回来的是一段切片，两者在举证时的分量不一样。

## 决策

**FAQ 独立成层，精确关键词匹配，排在检索之前，命中就返回，不进入检索。**

```
转人工 → FAQ → 检索 → 拒答
```

FAQ 的判据是关键词**字面包含**，不是相似度：

- 关键词一律取业务词（`多久发货`、`包邮`、`优惠券`），不用虚词（`怎么`、`可以`）。虚词会把一切问题都吸走，拒答就形同虚设。
- 短于 2 个字的关键词不参与匹配（`券`、`钱` 这种单字误命中率太高）。
- 多条命中时选**命中词总长度更长**的那条：`退货` 比 `快递` 更专指，长词命中通常意味着问题更具体。同长按声明顺序，先声明的优先级更高。

`MIN_KEYWORD_HITS = 1` 看着很松，但它成立的前提是"关键词本身足够专指"——这个前提写在常量旁边，因为放宽它就是放松整个拒答机制。

## 后果

- 得到：FAQ 的答案和检索质量、网络状况、向量端点健康度全部解耦。有测试锁住这一点：把 `rag_service.search` 换成抛异常，`包邮吗？` 仍然正常回答。
- 得到：答案可追溯。引用直接指向「FAQ：包邮吗？运费多少？」，客户质疑时能对上原文。
- 得到：常见问题不消耗 embedding 调用。10 条 FAQ 覆盖了大部分进线，省下的是真金白银的 token 和延迟。
- 付出：FAQ 是手工维护的表。新增业务话术（比如"能不能开发票到公司"）必须登记关键词，否则会掉到检索或拒答。这是刻意的取舍：**能直答的必须是确定的**。
- 付出：关键词匹配不懂同义改写。「发货快吗」不含任何已登记关键词，会落到检索。要解决这个得上同义词表或小模型分类，但那是另一件事，不能靠"把 FAQ 塞进检索"顺带解决。
- 重新考虑的条件：FAQ 条目涨到几十条、关键词开始互相冲突时，字面匹配会撑不住。那时应该换成意图分类器，而不是退回检索。
