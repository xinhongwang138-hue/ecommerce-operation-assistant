# 0016. 审批只留痕，不做自动通过/驳回

- 状态：Accepted
- 日期：2026-10-30
- 影响范围：`api/app/contracts/service.py`（`approve`）、`web/src/components/contract-panel.tsx`

## 背景

评分做出来之后，最自然的下一步是"自动判决"：分数 ≥50 就驳回，<20 就通过，中间的转人工。流程上很吸引人——省掉一个人的判断。

但合同是能拿去起诉的东西。两个具体问题：

**第一，规则分不覆盖合同的全部。** 一份合同可能账期、定金、违约金全部合规，但把独家经销权写进去了。规则没这条，分数是 0，自动通过。系统不知道自己不知道。

**第二，锅要有人背。** 自动通过的合同出了问题，追责时没有签字的那个。审计问"谁批的"，系统答"分数低于 20"。这在任何公司都过不了。

再往深一层：审批的价值不在"通过"这个动作，在**签字前有人真的看过**。自动判决最坏的地方不是判错，是让"看过"这件事不再发生。

## 决策

**系统只出风险清单，签不签由人签。审批记录只追加，不改写。**

```
决策只有三种：approved / rejected / changes_requested
每条记录带：决策人、时间、意见、以及当时的风险快照
改结论 = 再写一条，历史两条都在
```

**唯一的技术约束：高风险合同点「通过」必须写理由。**

不是拦住你——拒绝是 422，写了就过。要求的是"这个决定要附一句为什么"，比如「账期已与对方谈到 45 天，先用这一版签约」。没有这句话，"通过"就只是一个点击。

为什么只约束高风险：低风险合同本来就没什么好说的，强制写理由只会催生"ok"「已阅」这类废话，反而降低记录的价值。

**风险快照必须存下来。** 规则会改版，合同条款也会再谈一轮。事后要能回答"当时我看到的是哪几条风险"，只能靠审批那一刻的快照，不能靠回查当前的风险表。

## 后果

- 得到：每条审批都能对上"谁、什么时候、看到几条风险、为什么这么定"。这是审计要看的东西。
- 得到：系统边界清晰。它不承诺"这份合同没问题"，只承诺"这几条值得你看"。说得少，但说的都对得上。
- 付出：没有自动化的效率收益。审批人必须真的点开、真的写一句。这是设计目标，不是缺陷。
- 付出：`risk_snapshot` 是 JSON 冗余存储，规则改版后旧快照与新风险表会对不上。这是有意的：快照记的是历史事实，不跟着规则变。
- 重新考虑的条件：如果某类合同（如标准采购模板）已经经过法务逐条确认，可以为该模板登记一个"规则白名单"——但仍然要留痕，只是把"逐条看过"提前到模板评审那一次。
